# PeriLoop (working name)

A perioperative task-and-escalation loop for elective orthopaedic surgery. It treats pre-op assessment as surgical-risk screening and follows each result and task to closure.

Built for the Future Health Digital Innovation Challenge 2026 (Abu Dhabi Department of Health, run on Hack2skill), Statement 3: "Closing the Screening-to-Care Loop".

Synthetic data only. Every patient in this repository is fictional. This is decision support for staff, not diagnosis. Clinical thresholds are drafts awaiting surgeon sign-off.

## Try it in 60 seconds

1. Open `index.html` in any modern browser. No install, no server, no login.
2. On the Overview tab, press **Play 2-minute story**. Seven short scenes walk through three fictional patients (Mdm Aisha 62, knee; Mr Wong 59, lumbar; Mr Farid 70, hip).
3. Open the **Patient phone** tab. Pick a patient, then tap one of the sample chips, or type your own message in English, Bahasa Malaysia or Chinese, and press Send. The reply comes from fixed approved text, and any alert appears on the Staff board.
4. Open the **30-case tests** tab and run the 30 tests. Each case has an expected outcome written before the engine was built.

## What each tab shows

- **Overview**: the guided 7-scene story, live stats, a live loop diagram showing where each patient sits in the loop, and each patient's checklist (12 shared items plus 2 procedure-specific items, each with an owner and due time). A chart section shows how the unseen-message tests went.
- **Patient phone**: a Telegram-style chat with a fictional patient, the sample chips, a free-text box, and "Your plan" showing that patient's remaining tasks. Replies are fixed approved text. Nothing is generated by a model.
- **Staff board**: the alerts raised for the staff group, a way to inject a result for a patient, and a case board showing open holds, overdue items and closures.
- **30-case tests**: the runner for the 30 hand-written fictional cases, showing expected against actual outcome for each.
- **How it works**: the rules behind the engine and the procedure packs.

## Eight outcome classes

- **EMERGENCY**: a red flag caught by fixed rules, handled before anything else.
- **SAME-DAY**: an alert needing same-day human attention.
- **HOLD**: an abnormal result, held with an owner until it is resolved.
- **OVERDUE**: a task past its due time, re-pinged to its owner and nudged to the patient, escalated after a cap of 3.
- **ROUTE**: a clinical question routed to a clinician. The bot never answers these (for example blood thinners, antibiotics, flying, stopping injections).
- **ASK**: an unknown question, sent to a clinician.
- **ANSWER**: a message the bot answers with fixed approved text.
- **CLOSE**: a task closed with attached evidence plus a clinician, or a documented clinician decision with a reason. "ok" is refused.

## How it is built

- One self-contained HTML file (`index.html` once renamed for hosting). Nothing else is needed to run it.
- The engine is plain JavaScript in the browser. There is no server and no database.
- No model in version 1. Patient replies are fixed approved text (draft).
- Procedure packs are data: knee replacement, hip replacement, ACL reconstruction, lumbar surgery, shoulder arthroscopy, foot and ankle. Adding a pack means adding data, not changing the engine.
- Deterministic scoring is kept separate from AI. Red-flag rules run before anything else.

## Evidence so far (be honest about it)

- 30 hand-written fictional cases, with expected outcomes written before the engine: all 30 pass. The author wrote the cases and the engine together, so this proves little.
- Haiku (an AI model, not a clinician) labelled the 30 cases blind and agreed on 24 of 30. The differences (C02, C13, C17, C19, C26, C29) need a surgeon.
- Unseen messages written by an AI model (not patients): the first set of 63 urgent messages in 3 languages had 34 of 63 escalated at first pass. Every miss went to a clinician queue, and none was answered by the bot. After widening the rules, a fresh set of 60 (30 urgent, 30 normal) had 26 of 30 urgent escalated at first pass, and 3 of 30 normal falsely escalated. Both sets were then tuned on, so only a new set counts.
- With 7 of 7, the one-sided 95% lower bound on true sensitivity is about 65%.

## Limits

- Not done: second clinician blind labelling.
- Not done: testing on real patient messages (not allowed in this challenge).
- Not done: any measured reduction in missed steps.
- Not done: model layer. A model (DeepSeek or another) is planned only as an optional second check that can raise but never lower an alert and never answers clinical questions. It is not built or tested yet.
- Not done: Malaffi and Sahatna integration.
- Not done: real messaging channel.
- Not done: real database or login.
- Plan, not done: Malaffi (Abu Dhabi health information exchange) and Sahatna integration would be a standards-based adapter on result and appointment feeds.
- Plan, not done: pilot at a clinic with an existing Telegram FAQ and red-flag triage bot, subject to written permission from the employer (Ministry of Health, Malaysia) and the clinic. That permission has not been obtained.
- The shared checklist includes insurer pre-authorisation, because Abu Dhabi elective inpatient care generally needs it. This comes from search snippets and is not confirmed from official pages.
- No revenue figure. The planned unit of value is one operation episode paid for by a hospital, starting with a pilot.
- A published-rate figure for missed steps (public literature) is still to be added with sources.

## Synthetic data statement

All patients, messages, results and clinicians in this repository are fictional or AI-written. No real patient data is used or stored. The page runs entirely in the browser.
